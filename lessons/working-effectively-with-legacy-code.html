Working Effectively with Legacy Code

Michael Feathers

2004 · first editionSoftware engineering · Testing · Legacy code5–8 minute read

Change risky code in controlled steps by building feedback around real behaviour, finding seams that isolate dependencies and sprouting new tested code beside the old.

Evidence lens. Feathers offers practitioner guidance distilled from consulting and deliberately simplified examples, not controlled evidence that each technique improves outcomes in every codebase. Tests and seams can reduce uncertainty, but characterization tests may preserve defects, unit isolation does not prove integration correctness, and the book's Java, C++, C and C# examples reflect 2004 tooling. The mechanisms remain useful when adapted to today's languages and service boundaries.

Idea 1

Build a feedback path before a bold change #

The idea

Feathers uses a strict working definition: legacy code is code without tests. The point is not to insult old software or declare tests sufficient for quality. It is to expose the practical problem: when current behaviour cannot be checked quickly, developers cannot tell whether a change improved the code or quietly damaged something else.

His change approach starts by identifying where behaviour must change, finding places to observe it, breaking only the dependencies needed to run that code, writing focused tests, then making the change and refactoring. Characterization tests capture what the system actually does so existing behaviour becomes visible before you decide what should change.

Applied interpretation. Treat feedback as an instrument panel, not a certificate. The first useful test is often the one that shortens the distance between a small edit and evidence about the behaviour at risk.

Why it matters

Without fast feedback, teams manage risk by avoiding structural improvement or relying on long manual checks. A focused harness makes small, safer changes possible and gradually grows understanding.

Apply it today

Choose one change you have been avoiding. Write the behaviour you intend to alter and one existing behaviour that must remain.

Name the nearest place you can observe both. Draft one focused test that would fail if the preserved behaviour moved.

Caveat or failure mode

A characterization test records observed behaviour, including bugs and accidental quirks, and only covers the paths you exercise. Preserve first when uncertainty is high, then decide explicitly which behaviour is correct; retain integration and system checks for effects a unit harness cannot see.

02

Idea 2

Find the seam and its enabling point #

The idea

Feathers defines a seam as a place where you can alter program behaviour without editing at that place. A call to a database, clock, filesystem or remote service becomes testable when another implementation can be selected while the caller stays unchanged.

Every seam has an enabling point: the place where the choice is made. It may be a constructor argument, overridden method, link configuration, build setting or another mechanism. Seeing both matters because a supposed abstraction is not useful for testing if there is nowhere to substitute the collaborator.

Applied interpretation. Read code as a map of choices, not just a sheet of text. The seam is where behaviour differs; the enabling point is the control you use to choose the test behaviour.

Why it matters

A well-placed seam lets you sense and separate a small area without rewriting its whole dependency graph. That can create just enough feedback for a safer change.

Apply it today

Pick one dependency blocking a focused test and mark the exact call whose behaviour you need to replace.

Then mark where the implementation could be chosen. Prefer an explicit object seam such as an argument or constructor when the code allows it.

Caveat or failure mode

Not every indirect call is a useful seam, and test-only indirection can make production design harder to understand. Build or link seams can also hide differences between test and production. Use the smallest explicit substitution that preserves real behaviour and keep broader integration checks.

03

Idea 3

Sprout tested behaviour beside the risk #

The idea

Under time pressure, Feathers offers Sprout Method and Sprout Class for adding behaviour when the surrounding code cannot yet be placed under test. Write the new logic in a new method or class that can be developed with focused tests, then make the smallest delegation from the old code.

This does not make the legacy area safe or clean. It creates a small island of understood behaviour and prevents the new rule from becoming another untestable tangle. A sprout class is especially useful when the new work has a distinct responsibility or the old class is already overloaded.

Applied interpretation. Use a sprout as a bounded risk decision: move the new logic to a testable boundary and keep the unverified edit at the connection point small enough to inspect.

Why it matters

Waiting for a full rewrite can delay useful change indefinitely, while inserting more logic into an untested method increases future risk. A sprout provides a middle path.

Apply it today

For one urgent change, separate the new calculation or decision from the code that triggers it.

Choose a method if the behaviour fits the current responsibility; choose a class if it introduces a new responsibility or needs its own dependencies. Test the new unit before adding the single delegation.

Caveat or failure mode

A sprout adds indirection and tests only the new unit, not the old call path or integration. Repeated sprouts can fragment a design. Use them to improve the local trajectory, then add broader coverage and consolidate responsibilities when evidence and time permit.

Question 1 of 6 · Idea 1 · ConceptWhat is the main purpose of a characterization test when entering unfamiliar legacy code?

Characterization records what the code does, which can include bugs or quirks. Correctness still requires a separate decision about intended behaviour.

Capturing current behaviour creates a reference that exposes movement when the code changes, without certifying the behaviour as right.

Focused unit feedback can complement integration checks, but it cannot replace effects and paths outside the harness.

Intended requirements describe what the system should do. Characterization begins with what the implementation actually does.

A characterization test makes current behaviour observable before change. It supports comparison and learning, but it does not prove that the captured behaviour is correct or complete.

Question 2 of 6 · Idea 2 · ConceptWhich pair correctly distinguishes a seam from its enabling point?

Observation and assertion belong to a test feedback path, but they do not define the substitution site and the place where its choice is made.

A seam can exist in production design without containing test code. The enabling point selects an implementation rather than removing tests.

A seam may help isolate a dependency, but exposing private state is not what enables behaviour substitution.

Behaviour varies at the seam, while the enabling point is where production or test code chooses the variation.

The seam is the place whose behaviour can be replaced without editing there. The enabling point is the separate control that chooses which implementation or behaviour is used.

Question 3 of 6 · Idea 3 · ConceptWhat does a Sprout Method or Sprout Class primarily accomplish?

The new logic gains focused tests, while the untested legacy edit is reduced to a small delegation.

The sprout's tests cover the new unit, not every path through the surrounding component or its public interface.

A sprout can improve the local trajectory, but it is not an incremental rewrite plan and leaves most old code in place.

Sprouting is a bounded tactic for the new behaviour, not a requirement to redesign every responsibility first.

A sprout isolates new behaviour so it can be tested while keeping the required edit to the legacy area narrow. It does not certify or replace the surrounding code.

Question 4 of 6 · Idea 1 · ApplicationA team must modify an untested billing rule while preserving current invoice totals elsewhere. What is the strongest first move?

Refactoring before feedback can disturb behaviour the team does not yet understand. Establish an observable baseline first.

An end-to-end test can help, but accepting any stable output fails to distinguish preserved totals from incorrect ones or isolate the rule at risk.

The change point, test point and minimal dependency break create focused evidence about the totals that must remain stable.

A manual checklist may add evidence, but it is slower, harder to repeat and less focused than an automated observation around the affected behaviour.

The safe-change path identifies what will move, what must stay, and where both can be observed. It breaks only the dependencies needed to create focused feedback before altering the rule.

Question 5 of 6 · Idea 2 · ApplicationA method constructs a concrete payment client and calls it immediately, so the call cannot be replaced in a test. What is the clearest next step?

An argument or constructor becomes the enabling point where a test can select a substitute without changing the call site.

Inspecting private state does not provide a clean choice of behaviour at the payment call and couples the test to implementation details.

A retry may change production resilience, but it does not let the test replace or observe the payment dependency directly.

Moving the same construction hides it in another method but still provides no enabling point for choosing a substitute.

Passing the collaborator into the code creates an explicit enabling point. The call can then cross an object seam to a production client or a controlled test substitute.

Question 6 of 6 · Idea 3 · ApplicationAn urgent pricing calculation must enter a 900-line untested method. The calculation has clear inputs and outputs. What best applies the sprout technique?

Inlining adds more untested logic to the riskiest area and postpones the feedback that would make the change safer now.

The new unit can be tested independently, and the old method changes only at the narrow delegation point.

Full refactoring may eventually help, but it expands the immediate unverified change when the urgent need has a separable boundary.

Logging can aid observation, but stable output is not focused evidence that the new calculation is correct or safely integrated.

The clear input-output boundary makes the new calculation a good sprout candidate. Focused tests cover the new logic while one narrow delegation limits the unverified legacy edit.

Today's experiment · 10 minutes

Draw one safe-change path

  1. Pick a small change you expect in risky code. Write the new behaviour and one behaviour that must remain.
  2. Mark the change point and the nearest place you can observe the preserved behaviour.
  3. Name the dependency preventing a focused test. Mark a candidate seam and its enabling point.
  4. Decide whether the new behaviour could sprout into a tested method or class with one narrow delegation.
  5. Write the smallest first test and one integration check that would still be needed.

Observable result: You finish with a bounded route from risky change to observable feedback, plus the uncertainty that route does not cover.
