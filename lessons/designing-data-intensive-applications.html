Designing Data-Intensive Applications

Martin Kleppmann and Chris Riccomini

2017 · second edition 2026Software engineering · Data systems · Distributed systems5–8 minute read

Choose data systems from explicit workloads and guarantees, evolve formats for mixed-version reality, and treat a timeout as uncertainty rather than proof of failure.

Evidence lens. Kleppmann and Riccomini compare mechanisms, research and production experience rather than prescribing one universal architecture. The models for compatibility and partial failure are technically strong; product choices, thresholds and operational trade-offs remain context-dependent. This lesson uses the substantially updated 2026 second edition and keeps tool-specific claims secondary to durable principles.

Idea 1

Define the workload before choosing the system #

The idea

Kleppmann and Riccomini frame data-system architecture as a set of trade-offs among functional needs and qualities such as reliability, scalability, performance, maintainability and evolvability. A technology is not simply scalable or fast in the abstract; its behaviour depends on the operations, data volume, access pattern, failure tolerance and change rate it must support.

They therefore begin with workload and nonfunctional requirements. Load parameters such as requests per second, read-to-write mix, item size, data growth and hot-key concentration make a design claim testable, while latency percentiles and failure semantics say what acceptable service actually means.

Applied interpretation. Replace product-first architecture debates with a requirements envelope. Record the critical operation, expected load shape, acceptable tail latency, required correctness and growth horizon before comparing tools.

Why it matters

Teams can spend days debating database brands while hiding the assumptions that would decide the question. Explicit parameters turn preference into a falsifiable design and reveal when a simpler single-node or existing system is sufficient.

Apply it today

Choose one proposed data or integration component. Write its most important read or write operation and the peak load shape it must handle.

Add one tail-latency target, one correctness guarantee and one expected change over the next year. Compare options only against that small envelope.

Caveat or failure mode

Early numbers are estimates, and requirements can conflict or change. Do not manufacture false precision or demand every desirable property at once; record uncertainty, test the sensitive assumptions and revise the envelope with production evidence.

Idea 2

Design schema change for mixed-version reality #

The idea

The authors argue that applications and their stored data inevitably evolve, while deployment is rarely instantaneous. Old records remain after new code ships, and rolling deployments leave old and new processes active together. A format change must therefore be judged by how different versions read one another's data, not only by whether the latest code works with itself.

Backward compatibility lets newer code read data written by older code; forward compatibility lets older code read data written by newer code. Additive fields, explicit defaults, tolerant readers and staged rollouts can preserve both directions long enough for a safe transition.

Applied interpretation. Treat a schema rollout as a compatibility window, not one deployment event. Map which producer and consumer versions coexist, then order the change so every live edge remains readable.

Why it matters

A change can pass unit tests and still fail when an old worker reads a new message, a new release encounters an old row, or a rollback restores code that no longer understands current data. Compatibility makes those temporal dependencies explicit.

Apply it today

For one upcoming field or event change, list every writer, reader and stored copy that may still use the old format during rollout or rollback.

Choose an order: first make readers tolerate both forms, then introduce the new write, observe coexistence, migrate old data if needed and remove compatibility only after evidence shows it is unused.

Caveat or failure mode

Additive evolution is not free forever. Some semantic changes cannot be made safe with optional fields, and permanent tolerance creates ambiguity and maintenance cost. Define an observation period and a deliberate cleanup or translation boundary.

Idea 3

A timeout leaves the outcome unknown #

The idea

Kleppmann and Riccomini emphasise that distributed systems fail partially. A request can be lost, the server can be slow, the operation can complete while its response is lost, or the caller can pause. From a timeout alone, the caller cannot distinguish these cases.

A timeout is therefore a limit on knowledge, not evidence that the operation was rolled back. Blindly retrying a non-idempotent action can duplicate a payment, order or message. Stable operation identifiers, idempotent handling, status checks and reconciliation turn uncertainty into a state the system can manage.

Applied interpretation. Give every side effect an uncertainty path. Decide what the caller shows, which identifier survives a retry, how completion is verified and who reconciles an operation that remains unresolved.

Why it matters

Many severe duplicate-action bugs begin with the reasonable but false sentence, 'It timed out, so it failed.' Designing the unknown state explicitly protects users and makes recovery observable instead of depending on luck.

Apply it today

Choose one remote action with a side effect, such as creating an order, sending a notification or updating a case. Ask what a timeout proves about its outcome.

Write the stable operation ID, safe retry rule, status or reconciliation check and user-visible state for an unresolved result.

Caveat or failure mode

Idempotency is scoped, not magical. Keys can expire, downstream side effects may not share the guarantee, and indefinite retries can amplify overload. Bound retry timing, document key scope and retain a reconciliation path for ambiguous operations.

6 questions not yet answered.

Question 1 of 6 · Idea 1 · ConceptWhat makes a claim that a data system is scalable meaningful in this lesson?

Distribution can support some growth patterns, but it also adds coordination and failure modes. It does not define the workload or required service.

A stated workload, growth path and service target make the scalability claim specific enough to test and compare.

A benchmark can supply evidence, but only when its operations, data shape and guarantees resemble the actual workload being designed.

Organisational consistency can reduce operating cost, but copying a pattern does not show that it fits this workload and its guarantees.

Scalability is a relationship between a system and a changing load. The load parameters, required service and growth path must be visible before the claim can be evaluated.

Question 2 of 6 · Idea 2 · ConceptWhich condition best describes a schema change that supports a rolling deployment?

An atomic boundary is often unavailable across services, workers, clients and stored records. The lesson designs for version overlap instead.

Migrating all stored data before traffic resumes can be costly and still does not protect messages or processes that remain on the old version.

Tolerant reading is useful, but disabling validation entirely can admit malformed or semantically unsafe data rather than defined compatibility.

New readers accepting old data provide backward compatibility, while old readers safely handling new data provide forward compatibility.

During a rolling deployment, both versions may read data written by the other. The transition needs backward and forward compatibility across that coexistence window.

Question 3 of 6 · Idea 3 · ConceptWhat can a caller conclude when a remote write reaches its timeout?

No response does not prove rejection. The request may be delayed, lost, still running or already committed without its response reaching the caller.

The server may still be working, but that is only one possible state and the original connection may never deliver a response.

A timeout is an observation about elapsed time and knowledge, not a definitive statement about the remote side effect.

A lost response after completion is possible, but so are a lost request and slow or failed processing. The caller cannot select one case from the timeout alone.

The caller observes only the absence of a timely response. Several realities can produce that observation, including no execution, ongoing execution and completed execution with a lost response.

Question 4 of 6 · Idea 1 · ApplicationA team says it needs a distributed database because traffic may grow. What is the best first step?

A product trial can come later. Default benchmarks do not first establish which operations and guarantees the system must support.

These parameters expose what growth means and create a basis for testing whether distribution is necessary and which trade-offs fit.

Operational familiarity is relevant, but selecting first risks fitting the requirements to the product rather than testing the product against them.

Service splitting can add network and consistency problems before the original load, bottleneck or service target has even been defined.

The architecture should follow the actual pressure and required behaviour. A small requirements envelope may justify distribution, reveal a different bottleneck or show that a simpler system is enough.

Question 5 of 6 · Idea 2 · ApplicationA producer will add an optional field while old consumers remain active. Which rollout is safest?

Tolerant consumers remove the dangerous edge first; new writes can then begin while both forms remain readable and observable.

This makes production failures the compatibility test. An old consumer may reject the new record before a patch can be deployed.

Coordinated downtime may be possible in a small system, but it removes rollback flexibility and often cannot cover clients, queues or stored data.

A second type can help for a truly new meaning, but a simultaneous cutover recreates the same version-coordination risk.

Preparing readers before new writes creates a compatibility window in which old and new formats can coexist. Observation and later cleanup keep the temporary tolerance intentional.

Question 6 of 6 · Idea 3 · ApplicationA payment request times out after it is sent. What is the safest next action?

A new identifier can turn one uncertain charge into two independent charges. Preserve the logical operation's identity across recovery.

The stable identifier, status check and reconciliation path manage uncertainty without creating a second logical payment.

Failure is only one possible outcome. Asking for another submission can duplicate a charge that already completed before its response was lost.

Sending the request does not prove the gateway accepted or committed it. Recording success would replace uncertainty with an unsupported claim.

Preserving identity lets the system discover or repeat the same logical operation without inventing a second charge. A pending state is more honest than guessing success or failure.

Today's experiment · 10 minutes

Write a one-page data-system assumption card

  1. Name one important operation and write its peak load shape plus one tail-latency or reliability target.
  2. Describe one likely data-format change and list the old and new readers and writers that would coexist.
  3. Choose one remote side effect and write what a timeout leaves unknown.
  4. Add a stable operation ID, verification step or reconciliation owner, then circle the assumption you need to test first.

Observable result: You finish with one inspectable card connecting workload, evolution and partial-failure recovery to a real system decision.

One-sentence takeaway

Design the data system around explicit demands, planned coexistence and honest uncertainty, because the hardest failures live in assumptions that were never written down.
